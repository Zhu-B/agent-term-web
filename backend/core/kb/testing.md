# C 测试与验证

「测试全过但用户一用就出事」「我这儿过换个环境就红」这一类.
核心哲学: **测试跑的那条路, 必须和用户真实走的那条路是同一根线**.

---

### C1 环境依赖假绿: 带某种环境变量全过, 裸跑必红

- 现象: 同一测试命令, 你的 shell 里 PASS, 干净环境(或别人机器)FAIL.
- 根因: 环境变量被**继承**到子进程改了行为(经典: `PYTHONIOENCODING=utf-8` 掩盖了
  B1/B2 的编码坑, 所有 child 都恰好走了 UTF-8 路).
- 判据: 两种环境同一命令结果不同 = 假绿实锤.
- 对策: 回归网**至少裸环境(不带任何本地私有 env)跑一遍**; 发现假绿先修被测代码
  (让它在任何环境都对), 而不是补环境变量.
- 出处: agent-term _verify spawn:MCP(2026-10-13, 裸跑红/带 env 绿).

### C2 测试直调绕过了真正出事的 UI 入口路径

- 现象: 功能有真 bug, 回归全绿(用户一用就撞).
- 两个经典形状:
  ① 直调内部函数绕过对话框入口(建版 TclError 在按钮回调里, 冒烟直接调 `_do_create` 从没经过);
  ② 只查"数据面"不查"用户可见面"(查了行 Frame 的 pack 与 `.get()` 值, 没查控件
     `winfo_ismapped` —— 输入框没 pack 隐形照样全绿, 见 A1).
- 对策: 关键断言必须**走用户真实路径**(真开对话框填内容真点按钮) + 查用户能看到的东西
  (mapped/manager/渲染像素), 而不是只查数据值.
- 出处: version.py 建版(2026-10-13); frontend VoicePanel(2026-10-13).

### C3 断言拿"历史累计量"判"本次行为"

- 现象: 断言偶发红/红得莫名其妙.
- 根因: 数了历史所有记录(如"弹窗总数")而不是本次增量.
- 对策: 改**前后差值比较**(弹窗前记数, 后比 delta).
- 出处: panel_smoke §14 弹窗计数(2026-10-13).
- **追加(2026-10-13, 问题库接入时实锤)**: 更隐蔽的一种=**两边基准不同源** —— "压缩前后
  对话字符"断言拿**压缩后**的新系统提示词长度去减**压缩前**的旧总量: 系统提示词加一行
  (BASE_RULES 长基底), 差值就塌(conv_before 397→177 误报"对话没变小"; 该断言此前已被
  提示词增行顶破过三次 0.5→0.6→0.65, 都是同一病根). 修法: 基准各取各时刻(压缩前用
  压缩前的, 压缩后用压缩后的). **长基底参与相减的断言尤其脆** —— 能直接量目标部分就
  直接量, 别用"总量差"近似.

### C4 golden/回放归一化必须覆盖所有路径变体

- 现象: golden 对不上, 实际行为没变.
- 根因: 归一化(把沙箱绝对路径换成占位符)没覆盖某形态 —— 同一路径有**三种书写**:
  原生反斜杠、正斜杠、**JSON 转义的双反斜杠**(进 jsonl 里的样子).
- 对策: canon_line 统一处理三个变体(`raw` / `s.replace("\\","/")` / `s.replace("\\","\\\\")`);
  新场景进 golden 前先双跑确认稳定.
- 出处: agent-term _verify canon_line(2026-10-13, Windows 绝对路径进 golden 实测不归一).

### C5 打桩/走查必须用临时目录

- 现象: 测试污染了真实数据(记忆卡/配置/媒体池被写).
- 对策: 一切写盘行为在 `tempfile.mkdtemp` 沙箱里跑, 用环境变量缝
  (`AT_MEDIA_DIR`/`AT_CACHE_DIR`/重定向 HOME)把真实路径引开; 跑完清理.
- 出处: agent-term 家法(2026-10-12/13 多次教训).

### C6 golden 重铸必须过结构审计 + 双跑稳定

- 现象: 重铸 golden 后把真实回归错误一起"重铸"掉了.
- 对策: 重铸时逐字段走一遍 diff, 只允许预期字段变化(路径归一/新增字段), 别的变化要能解释;
  重铸后连跑两遍确认确定性. 审计过程要留档说明.
- 出处: agent-term 历次 golden 重铸(2026-10-12/13).

### C7 tkinter 断言: 几何异步, 键盘合成不可靠

- 现象: `geometry()` 后立刻读 `winfo_x` 是旧值; `event_generate` 键盘事件不触发真实行为.
- 对策: 几何断言读**状态属性**(如 `_edge_hidden`)或给容差; 鼠标合成 `event_generate
  ('<Button-1>')` 可靠、键盘不可靠 —— Entry 回车这类只能真人验或直调回调.
- 出处: desktop-workbench(2026-10-08).

### C8 探针法: 症状被中间层兜住看不出真错

- 现象: 工具层把异常统一兜成"tool crashed", 真错(NameError 等)被遮蔽.
- 对策: 写**最小探针脚本**绕开中间层直捣黄龙(直接 import 被测模块跑那一段), 让异常裸奔.
- 搭子: G5(修复前先写"必红"的锚) —— 探针确认病灶后, 把探针变成回归锚.
- 出处: agent-term vision_selfcheck 忘 import base64 被兜成 crash(2026-10-13).

### C9 沙箱复现法: 造"全新机器"排除环境

- 现象: 用户报"我什么都没配却能用(或不能用)", 争论代码干不干净.
- 对策: 临时重定向 HOME + 清空所有 key 环境变量, 起一个"全新机器"实例复现 ——
  干净机器正常 → 问题必在用户环境的残留(见 G1).
- 出处: agent-term qwen 无 key 之谜(2026-10-13, 沙箱证明代码干净).

### C10 断言依赖 mtime 排序: 同秒落盘并列会偶发红

- 现象: 测试里连续写两个文件再断言"按修改时间倒序", 偶发拿到反序 ——
  两文件同秒落盘 mtime 相同, 排序并列落到 listdir 顺序(不确定).
- 判据: 断言里出现"新卡在前/最新在前"且红绿随机; 失败详情里顺序整体反转.
- 对策: 依赖 mtime 排序的断言先 `os.utime` 把时间戳定死(如 100/200)再断言;
  或断言改成与顺序无关(集合/字典).
- 出处: _verify.py memory_selfcheck "memory:list 摘要+新卡在前"(2026-10-14, 1/17 概率红).

### C11 断言里的全局计数会被"后来加的调用"污染

- 现象: 老断言 `len(seen) == 1` 突然红了 —— 不是功能坏, 是同一测试块里**后来加了
  新的打桩调用**, seen 里多了一条.
- 根因: 断言绑在"到此为止共几次"这种全局计数上, 对测试块内的增量不鲁棒.
- 判据: 红的时候 seen 内容其实都对, 只是条数对不上; 删掉新增调用就绿.
- 对策: 断言**看具体元素**(seen[0] / seen[-1] 的值), 不看总数; 真要数数就立刻断,
  别隔了几次调用再数.
- 出处: agent-term spawn 自检加 M28 入参用例(2026-10-15), r2 后追加 r3 打桩把
  `len(seen)==1` 顶红.

### C12 复制测试样板时, 谓词闭包捕获的容器要跟着换新

- 现象: 第二组用例断言读自己的捕获列表, 永远是空的(或反之: 读旧列表仍被新用例
  填充 → **假绿**, 更险).
- 根因: 复制上一组的 RuleProvider 规则/捕获谓词时, 闭包里 append 的还是**上一组
  的列表** —— 功能代码毫无问题, 纯测试装配错位.
- 判据: 单独复现第二组用例全绿, 并进大块就红; 红的那组断言读的列表从头到尾
  没被写过.
- 对策: 复制样板后逐个过一遍闭包捕获(容器/计数器/sentinel); 捕获谓词写成
  工厂或就地新函数(每组自己的 `_cap_xxx`), 别复用上一组的.
- 出处: agent-term M32 识图自检(2026-10-16), ④b 复用 ④a 的 `_cap_child` 往
  `child_caps` 塞, `child_caps2` 恒空必红.
